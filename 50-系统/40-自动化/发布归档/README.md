# 发布归档

公开发布完成之后，把结果写回知识库，并把这一轮生产文件从活跃区收好：登记正式稿的平台字段，创建发布反馈卡，更新源头书签，归档母稿、口播稿和成稿包。这是 [[50-系统/20-流程/个人知识库工作流|个人知识库工作流]] 第六节「发布与回流」里能自动完成的部分。

## 安全边界

- **这个脚本不发布任何东西。** 它不调用微信或 X 的任何接口，不打开浏览器，不碰 `Publish` 按钮。它只在人已经在平台上完成公开发布之后运行，把已经发生的事记下来。公开发布始终是用户动作。
- 只收拾这篇正式稿明确链接到的母稿、口播稿和成稿包，不按标题猜测，也不批量移动相似文件。传进来的路径不在知识库内、或者不在正式稿目录下，直接报错退出。
- 归档前先检查目标位置。同名文件已经存在时，整次登记会在写入任何内容之前停下，留给人判断，绝不覆盖。
- 不伪造平台数据。公开链接和发布时间都可以留空；一旦填写，公开地址必须是真的公开地址，草稿编辑器和创作者后台地址会被拒绝，时间也必须带时区。没有填写平台时间时，反馈期限从本地确认发布的时刻开始计算，但不会把这个时刻冒充平台发布时间。
- 同一篇稿子在同一个平台已经记过另一个公开地址时，报错停下，不覆盖。哪个是对的只有人知道。
- 反馈卡只填空，不覆盖。已经写完的 24 小时复盘不会被打回 `pending`，正文里手写的数字也不会被重建的模板冲掉。

## 用法

```
python3 record_published.py \
  --article "40-发布/10-X长文/2026-07-19-AI内容越多平台越需要回答这是谁说的.md" \
  --platform x
```

`--platform` 取 `x`、`wechat`、`shipinhao`、`douyin`、`xiaohongshu`，每个平台各写各的字段，互不影响。同一篇稿子发几个平台就跑几次。`--url` 和 `--published-at` 都是可选项；需要追溯时再填写，其中时间仍需使用带时区的完整格式。第一次登记会完成本地收尾；后续平台登记可以放心重跑，不会重复归档。加 `--dry-run` 只打印将要写什么，不落盘。

资料齐全时也可以一次写入：

```
python3 record_published.py \
  --article "40-发布/10-X长文/2026-07-19-AI内容越多平台越需要回答这是谁说的.md" \
  --platform x \
  --url "https://x.com/wangray/status/2079091643693863273" \
  --published-at "2026-07-19T23:30:50-07:00"
```

如果公开发布已经登记过，只是旧流程漏了本地收尾，可以单独补做：

```
python3 record_published.py \
  --article "40-发布/10-X长文/2026-07-19-AI内容越多平台越需要回答这是谁说的.md" \
  --closeout-only \
  --dry-run
```

确认预览后去掉 `--dry-run`。它只补归档，不改任何平台链接和发布时间。

### 口播视频

`--article` 传的是 `40-发布/50-口播视频/` 里的**逐字稿**，不是视频文件；视频本身不进知识库。一条视频一次发三个平台，就跑三次：

```
python3 record_published.py \
  --article "40-发布/50-口播视频/2026-07-24-个人级FDE第1集-被优化的人的下一站.md" \
  --platform douyin \
  --url "https://www.douyin.com/video/7530000000000000000" \
  --published-at "2026-07-24T20:10:00+08:00"
```

反馈卡自动换成 [[50-系统/30-模板/口播视频反馈|口播视频反馈模板]]——图文那张卡没有完播率和平均播放时长，而视频要先回答的是"有没有被划走"，套错模板等于三个平台的主指标一个都不记。`public_url` 只装得下第一个跑的平台，所以每个平台的链接还各自留一份（`douyin_url`、`xiaohongshu_url`、`shipinhao_url`），后两次运行的链接不会丢。三个平台的后台数据都要人去看，每跑一个就立一条 `<平台>_data_status: pending`。

视频号常常根本给不出可分享的公开网页地址，`--url` 可以直接省略；如果希望明确记录平台确实没有公开地址，也可以填固定字面量 `无公开链接`。三个平台的创作者后台地址（`creator.douyin.com`、`creator.xiaohongshu.com`、`channels.weixin.qq.com/platform`）和 X 的草稿编辑器地址一样会被拒。

## 它写了什么

**正式稿**：按平台写 `x_article_status` / `x_article_url` / `x_article_published_at`，或 `wechat_status` / `wechat_public_url` / `wechat_published_at`。其中 `status: published` 是发布事实，链接和时间是可选追溯资料；健康检查只会拦截已经填写却明显是草稿编辑器或创作者后台的错误地址。

**反馈卡**：`40-发布/00-内容反馈/` 下没有对应卡片就按 [[50-系统/30-模板/内容反馈|内容反馈模板]] 建一张，`due_at` 指向发布后 24 小时。已有卡片只补空字段。发的是公众号时立起 `wechat_data_status: pending`——后台数据要人去看。

**源头书签**：顺着正式稿找回它的 X 书签，标记 `processing_status: processed`，并记下 `published_file` 指向这篇稿。正式稿到书签之间隔着写作任务和审核卡，字段名还不统一（`source_note` 直接指书签，`source` 和 `content_pack` 指写作任务，`source_review` 指审核卡），所以脚本挨条试，最后用 `capture_id` 里的推文编号兜底——书签改名或换了月目录也还找得到。来源是网页剪藏、或者链子断了，就在报告里说「未找到」，不去改别的卡。

**发布后收尾**：正式稿链接到的文章母稿移到 `90-归档/30-创作记录/旧文章草稿/<年月>/`，独立口播稿移到 `旧口播草稿/<年月>/`，成稿包移到 `旧成稿包/<年月>/`。移动前会把相对图片链接重新换算，移动后会修复知识库里引用这些文件的链接。已经录完但没有确认公开发布的口播稿不会动；A/B 稿取舍、同名冲突和没有明确正式稿链接的历史文件也不会靠猜测处理。

## 它没做什么

「发布与回流」仍有三类内容要人判断，脚本每次运行都会把还欠的列出来：把可复用的观点写回 `20-知识/` 并更新 `knowledge_backfill_status`、标记已用角度并更新 `remaining_angles_status`、把候选选题改成 `partially-published` 还是 `closed`。本地生产文件会自动收好，但这些内容判断不会被机器代做。
