# 知识采集自动化

这套流程统一处理四种来源：

1. Web Clipper 新剪藏。
2. Ray 的 𝕏 新收藏。
3. 手机分享到 iCloud 投递箱的链接。
4. 微信读书新增或更新的书籍划线卡。

𝕏 书签会保存完整长帖、Article 全文和每一项图片或视频附件，不再只保存缩略正文。正文暂时获取失败时会保留原链接，并在后续同步中重试。

Article 的封面和插图只存在于详情接口，正文纯文本里没有它们，所以卡片会另起一节 `## Article 配图` 逐张列出地址、alt 说明，以及每张插图接在正文哪句话之后。接口偶尔只回 media_key 不回地址时，这一行仍然保留 media_key，方便事后追查。

历史书签需要补齐时运行：

`python3 knowledge_ingest.py repair-x`

它只修复已经存在的书签，不会把远端其他内容突然导入，也不会把历史书签重新塞进审核队列。已有的人工总结会保留。以后要添加个人想法，统一写在 `## 个人笔记` 下，后续刷新时会继续保留。

长文会按正文长度分批提炼，避免多篇长文挤在一次处理中而被截短。

新采集的原始内容保持不动。Codex 先生成位于 `10-创作/10-灵感/10-待评估/剪藏复核/` 的审核卡片；人工可以分别判断“是否沉淀长期知识”和“是否进入候选选题”，也可以让两条路径同时成立。处理完成后，审核卡会退出活跃入口，进入可追溯归档。系统不会永久删除原文。

审核选择的唯一规则保存在 `50-系统/40-自动化/review_protocol.json`。采集、仪表盘、健康检查和演示数据都读取这份协议；新增或改名选择时只改这里，旧文案只用于兼容历史卡片。

进入候选选题不会自动创建成稿包。只有确认近期要写、并明确本次角度后，才运行：

`python3 knowledge_ingest.py promote '<候选选题相对路径>' --angle '<本次角度>'`

正式写作任务保存在 `10-创作/20-写作任务/`；其余角度仍留在候选或主题地图。

当前使用 GPT-5.5，只处理新进入收件箱、网页剪藏、X 收藏和未处理的微信读书书籍卡，不扫描整个知识库。待本机 Codex 支持 GPT-5.6 Sol 后再升级。

## 运行频率

Mac 每 30 分钟检查一次。没有新资料时不会调用 Codex。

另外生成两类健康报告：

- 每天 18:00 生成知识库健康日报，只做本地统计，不调用模型。
- 每天 18:05 为内容目录生成一次本地版本快照；运行前会先同步微信读书，有异常时不会把系统文件或人工暂存内容混入快照。
- 每周日 09:00 生成知识库周报，使用 GPT-5.5 总结最近 7 天趋势和下周优先事项。
- Mac 在计划时间休眠时，会在下次唤醒后补跑一次。
- 每次生成日报或周报后都会自动回收历史报告：日报活跃区保留最近 7 天，周报活跃区保留最近 8 周；更早的报告分别归档到 `90-归档/40-系统报告/知识库健康日报/` 和 `90-归档/40-系统报告/知识库周报/`。保留期限可在 `config.json` 中通过 `daily_report_keep_days` 和 `weekly_report_keep_weeks` 调整。

健康日报除四个定时任务、采集与链接检查外，还包含这些结构检查：

- **属性 schema**：`20-知识` 中 `kind` 越界或残留旧字段（type/created/updated/knowledge_type）的笔记数。
- **待清理超期**：`90-归档/90-待清理` 中放置超过 90 天的目录，提醒人工确认删除。
- **创作健康**：候选池是否过大或过期、写作任务是否过多、发布反馈是否逾期、活跃审核目录中是否混入已处理卡。
- **关系健康**：知识地图覆盖、候选知识去向、发布记录关系，以及活跃内容是否还指向待清理区。
- **选题时效**：候选、续写和储备选题都必须有可重建的刷新日期；过期选题不会继续进入仪表盘的“当前候选”。

## X Article 发布检测

草稿由 X Article 管线推入平台草稿箱后（frontmatter 记 `x_article_status: draft` 和 `x_article_saved_at`），发布是人在平台上手动完成的动作。每 30 分钟任务里有一步自动确认发布结果，把「已发布」登记回知识库：

- 严格门控：只有 `10-创作/30-文章草稿/` 与 `10-创作/20-口播草稿/` 里 `x_article_status: draft` 且 `x_article_saved_at` 在 72 小时内的草稿才触发 API 调用；一次时间线调用（默认拉最近 50 条，`config.json` 的 `x_timeline_max_results`）覆盖本轮全部待确认草稿；超窗口不再轮询，留给工作台「登记发布」表单人工兜底。
- 门控字段的上游：这两个字段由 [rayskills](https://github.com/imraywang/rayskills) 的 `ray-x-article` skill 在把草稿推入 X 草稿箱时写入（`scripts/record_draft.py`，带时区 ISO 时间）。`draft-needs-cover` 等中间状态不触发检测；补齐封面重新记录为 `draft` 会刷新 `x_article_saved_at`，等于重开 72 小时窗口。不用该 skill 的话，手工在草稿 frontmatter 写这两个字段同样能接入检测。
- 调用前先本地对账：对应正式稿已经登记过 X 发布（比如走了工作台表单）时，直接把草稿这头的状态关上，不调 API。
- 匹配规则：帖子时间晚于 `x_article_saved_at`，且 Article 标题精确相等；发布前在编辑器里微调过标题的情况走高相似度兜底（阈值 0.75）。无论哪一档都要求唯一命中，多条命中、同一条帖子被两篇草稿匹配等不确定情况只记日志不动文件。
- 命中后：缺正式稿时先归档正式稿到 `40-发布/`（口径同知识仪表盘的登记发布），再调用 `../发布归档/record_published.py --platform x` 完成正式稿、反馈卡与源头书签归档（它会拒绝草稿编辑器地址），最后把草稿与成稿包的 `status` 置为 `published` 并写 `published_file` 链接。
- 手工验证：`python3 knowledge_ingest.py detect-x-articles --dry-run` 只打印会做什么，不写任何文件；去掉 `--dry-run` 立即执行一轮。
- 微信不做自动检测：个人订阅号的 freepublish/batchget 与 datacube 接口均无权限（实测 48001），公众号发布仍走工作台表单登记。

## 文件位置约定

- 脚本与配置在本目录（随 vault 同步）。
- 运行时状态与日志在 vault 外的 `~/.local/state/rays-brain/`（`state.json`、`logs/`、`health-snapshots/`），避免 iCloud 高频同步和冲突副本破坏去重状态；可用环境变量 `RAYS_BRAIN_STATE` 覆盖。
- 日报和周报的“最新”入口始终留在 `00-入口/20-日报/`；超过保留期限的历史报告按月份或年份进入 `90-归档/40-系统报告/`，不会永久删除。
- X 书签按月分目录、按标题命名：`30-资料/30-X书签/YYYY-MM/YYYY-MM-DD-<标题>.md`。标题取 Article 标题，短推取正文首句。推文 ID 保存在 frontmatter 的 `tweet_id`，去重与补抓都以它为准，不依赖文件名。
- Article 卡片的 frontmatter 还有 `article_image_count`，记录封面加插图的总张数。这个字段只在真的问过详情接口后才写，所以“没问过”和“确实一张图都没有”不会混淆：早期存下、还没有这个字段的旧卡片会在下一次同步时多发一次详情请求把配图补上，补完就不再为它多花调用。
- 新采集来源统一写 `source_url / published_at / created_at`；`source / published / created` 只用于兼容历史资料，不再由采集器生成。候选和写作记录中的发布稿链接使用 `published_file`，不与来源发布时间共用字段。
- 微信读书先导预览：`weread_preview.py <bookId|书名>` 输出一本书的简介、逐章目录（含字数）、全书热门划线 Top 20 和各章划线密度，用于配书时不买书先判断值不值得读、从哪读起；结果摘要写进选书清单的「先导预览」，划线原文是版权片段不进入公开发布物。
- 微信读书划线：`weread_sync.py` 把每本有笔记的书导出为 `30-资料/50-读书划线/《书名》.md`（书籍卡）。划线与想法在 `weread:begin/end` 标记内由脚本维护；标记外的「我的判断」「可提炼的长期知识」是人工区，重新同步不会覆盖。frontmatter 的 `capture_id`（`weread:<bookId>`）是书籍的稳定身份。需要环境变量 `WEREAD_API_KEY`（在 `~/.zshrc`）。默认增量（对比 state 里的 sort/划线数/想法数），`--full` 全量重拉；同步状态在 `~/.local/state/rays-brain/weread_state.json`。
- 微信读书审核：已处理书籍在首次接入时只登记为基线，不回灌待评估。新书或新增划线会把书籍卡改为 `unprocessed`，统一采集任务按 `bookId + 划线/想法版本` 去重后生成标准审核卡。任一人工分流动作完成后，原书籍卡恢复为 `processed`；由它生成的知识或候选选题都会保留原书籍卡链接。
- 新知识笔记的 frontmatter 只写规范字段：`kind`（按目标文件夹推导的枚举值）、`status: seed`、`origin`、`created_at` 以及来源追溯字段。
- 每日内容快照只处理明确列出的内容目录，运行状态保存在 `~/.local/state/rays-brain/content-snapshot-success.json`；详细边界见 `../内容快照/README.md`。

## 历史知识复核

`10-创作/10-灵感/10-待评估/存量知识复核/` 中的历史复核卡也由每 30 分钟任务执行：

- 保留：原笔记转为正式长期知识。
- 降级：移动到 `30-资料/20-参考资料/历史知识降级/`。
- 待清理：移动到按日期划分的可恢复归档。
- 合并：必须先写明合并目标并完成主笔记；条件不完整时停止执行，并显示在健康日报中。

每次执行前都会自动生成压缩备份；文件移动后会同步更新内部链接。复核卡会记录原始位置、当前文件位置和最终去向，并在处理后退出活跃入口。

## 一次性存量迁移

旧流程迁移默认只预览，不改文件：

`python3 migrate_content_flow.py plan`

确认后执行：

`python3 migrate_content_flow.py apply`

执行前会生成压缩备份。旧的自动成稿包进入可恢复创作归档，已确认在写的任务进入 `10-创作/20-写作任务/`，近期不写的候选进入 `10-创作/10-灵感/90-选题储备/`。

历史候选缺少时效字段时，可重复运行：

`python3 knowledge_ingest.py backfill-topics`

它只根据已有来源时间、创建时间和明确的刷新证据补齐字段，不编造新的事实。无法判断的候选会列出来，等待人工核对。

## 处理边界

- 新采集原文保持不动；历史知识只按人工勾选结果移动。
- 以网址、推文编号和内容记录避免重复。
- 已移入可恢复清理区的 X 书签编号仍参与去重，后续同步和历史修复不会把它们重新抓回活跃资料区。
- 正式知识必须人工批准。
- 失败任务留在队列，下一次继续尝试。
- 不永久删除文件；清理和合并后的旧稿进入可恢复归档。
